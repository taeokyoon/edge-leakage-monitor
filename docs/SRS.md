## 1. 문서 규칙

- 요구사항 계층 (ASPICE 4.0): 
    **STK** 이해관계자 요구사항(SYS.1) // 고객의 부탁
    >>>> 작성은 고객/PM, 요구공학 담당이 고객 말을 받아적음.
    >>>> 인수테스트 설계. "고객이 원한대로 되냐?"를 확인함
    **SYS** 시스템 요구사항(SYS.2) // SW가 지켜야 할 기준
    >>>> 작성은 시스템 엔지니어(개발)
    >>>> 테스터는 리뷰 -> 시스템 테스트 설계 (ASPICE)
    **SWR** SW 요구사항(SWE.1). // SYS 보다 구체적인
    >>>> 작성은 SW 개발자(SW 요구담당)
    >>>> 리뷰 -> SW 테스트/통합 테스트 설계
   SWR를 기준으로 테스트를 만들고, STK로 고객의 만족도를 확인함
   >>>> 그니까 검증은 STK, SYS, SWR를 모두 리뷰하고, 테스트케이스를 설계함

  하위 요구사항은 상위 ID를 "근거"에 적는다 (추적성).
- 모든 요구사항은 "~해야 한다" 형식으로, 하나에 한 가지만 적는다.
- 합격 기준: 합격/불합격을 가르는 숫자. 비고: 범위 밖 사항과 리뷰 번호(RV, `docs/TEST.md` 6장)
- 검증 방법 (ISO 26262-6 용어 기준)
  - 테스트: 요구사항 기반 테스트. 정해진 입력을 넣고 결과를 기대값과 비교해 합격/불합격 판정 (SIL·HIL·실기기)
  - 리뷰: 문서·코드·배선을 사람이 확인
  - 분석: 지표·계산·측정 데이터로 확인 (오경보율, 지연 시간 등)
- 상태: **구현** / **부분 구현** (구현된 부분은 비고에 적음) / **미구현**
- 파라미터 값은 `config/settings.yaml`을 따르며, 이 문서의 값은 현재 기본값이다.

## 2. 이해관계자 요구사항 (STK)

1.
   - ID - STK-01
   - 요구사항 - 시스템은 설비의 누설전류 추세를 주기적으로 감시하고, 절연 열화 의심을 주의·점검권고 단계별로 점검 담당자에게 알려야 한다.
   - 합격 기준 - 이상 시작 후 [TBD-05] 안에 주의를 알린다
   - 비고 - 보호(전원 차단) 기능은 범위가 아니다 (RV-01, RV-02)
   - 검증 - 테스트

2.
   - ID - STK-02
   - 요구사항 - 시스템은 습도([TBD-06] 범위)·운전 시간대에 따른 정상 변동으로 경보를 내지 않아야 한다.
   - 합격 기준 - 정상 변동 시나리오의 오경보율 [TBD-05] 이하
   - 비고 - 경보는 주의·점검권고 모두 포함 (RV-03~05)
   - 검증 - 분석

3.
   - ID - STK-03
   - 요구사항 - 시스템은 순간 노이즈(1시간 이하 급등 1회)로 경보를 내지 않아야 한다.
   - 비고 - RV-06
   - 검증 - 테스트

4.
   - ID - STK-04
   - 요구사항 - 경보는 설비 위치(동·라인·설비)와 함께 웹 대시보드에 표시되어야 한다.
   - 비고 - "경보"의 뜻은 7.2절 용어를 따른다 (RV-08)
   - 검증 - 테스트

5.
   - ID - STK-05a
   - 요구사항 - 점검 담당자는 웹 대시보드에서 점검권고를 확인 처리(ack)할 수 있어야 한다.
   - 검증 - 테스트

6.
   - ID - STK-05b
   - 요구사항 - ack하면 설비는 정상으로 돌아가고 점검권고 알림이 멈춰야 한다.
   - 비고 - RV-09
   - 검증 - 테스트

7.
   - ID - STK-06
   - 요구사항 - 시스템은 센서 고장(데이터 미수신)을 이상 경보와 구분해 알려야 한다.
   - 비고 - 센서가 잘못된 값을 계속 내는 고장은 감지 범위가 아니다 (RV-10)
   - 검증 - 테스트

8.
   - ID - STK-07a
   - 요구사항 - 장치와 서버 사이의 통신은 암호화되어야 한다.
   - 비고 - RV-11 (STK-07을 3개로 분리)
   - 검증 - 테스트

9.
   - ID - STK-07b
   - 요구사항 - 등록되지 않은 장치는 접속할 수 없어야 한다.
   - 검증 - 테스트

10.
   - ID - STK-07c
   - 요구사항 - 장치는 다른 설비의 데이터를 발행할 수 없어야 한다.
   - 검증 - 테스트

11.
   - ID - STK-08
   - 요구사항 - 현장에서 장치의 화면(OLED)·표시등(LED)으로 현재 상태(정상·주의·점검권고·센서장애)를 확인할 수 있어야 한다.
   - 비고 - RV-12
   - 검증 - 테스트

12.
   - ID - STK-09
   - 요구사항 - 시스템은 0~3.3V 저전압 모사 신호만 사용하고, 상용 전원(220V/380V) 설비에 연결하지 않아야 한다. (제약)
   - 검증 - 리뷰

13.
   - ID - STK-10
   - 요구사항 - AI 감지 성능을 재현 가능한 시나리오로 정량 평가할 수 있어야 한다.
   - 합격 기준 - [TBD-05]
   - 검증 - 분석

14.
   - ID - STK-11
   - 요구사항 - 시스템은 반복되는 순간 급등을 주의로 알려야 한다.
   - 비고 - RV-07 (기존 설계 문서에만 있던 요구를 STK로 올림)
   - 검증 - 테스트

## 7. 개요

### 7.1 시나리오 7종 (`src/leakmon/scenario.py`)

가상 설비의 누설전류·습도를 만들어 내는 "가상 플랜트 모델"이다. SIL 검증의 입력 데이터이며, 5단계에서는 같은 값을 DAC 전압으로 출력해 HIL 입력으로 쓴다.

공통 조건 (모든 시나리오)
- 시작 후 **가상 1일은 정상 운전**, 그 뒤에 이상(또는 정상 변동)이 시작된다.
- 정상 누설전류 = 4.5mA + 습도 영향(습도 1%p당 0.08mA) + 가동 시간대(08~18시) 0.4mA
- 습도는 하루 주기로 ±5%p 변한다. 측정 노이즈가 섞인다.
- 같은 시나리오·같은 seed면 노이즈까지 똑같이 재현된다.

1.
   - 번호 - 1
   - 이름 (코드) - 정상 운전 (`normal`)
   - 무슨 일이 일어나나 - 이상 없음
   - 기대 결과 (요구사항) - 경보 없음
   - 현재 결과 (고정 임계값 방식) - 경보 없음 (7일)
   - 검증 목적 - 오경보가 없는지 (STK-02)

2.
   - 번호 - 2
   - 이름 (코드) - 완만한 상승 (`gradual_rise`)
   - 무슨 일이 일어나나 - 누설전류가 하루 0.5mA씩 계속 오름 (절연 열화)
   - 기대 결과 (요구사항) - AI가 고정 임계값보다 먼저 감지
   - 현재 결과 (고정 임계값 방식) - 4일 10:00 주의 → 주의·정상 반복 → 9일 10:00 점검권고
   - 검증 목적 - 조기 감지 (STK-01)

3.
   - 번호 - 3
   - 이름 (코드) - 습도 상승 (`humidity_rise`)
   - 무슨 일이 일어나나 - 습도가 2일에 걸쳐 +35%p 오른 뒤 유지 → 누설전류 약 +2.8mA. **고장이 아닌 정상 변동**
   - 기대 결과 (요구사항) - 경보 없음
   - 현재 결과 (고정 임계값 방식) - 2일 10:00 주의 (**오경보**)
   - 검증 목적 - 정상 변동과 고장 구분 (STK-02)

4.
   - 번호 - 4
   - 이름 (코드) - 순간 급등 1회 (`short_spike`)
   - 무슨 일이 일어나나 - 1시간 동안만 +6mA 튄 뒤 복귀
   - 기대 결과 (요구사항) - 경보 없음, "순간 튐" 기록
   - 현재 결과 (고정 임계값 방식) - 경보 없음 (기록 기능은 미구현)
   - 검증 목적 - 노이즈 억제 (STK-03)

5.
   - 번호 - 5
   - 이름 (코드) - 반복 순간 급등 (`repeated_spike`)
   - 무슨 일이 일어나나 - 6시간마다 1시간씩 +6mA, 계속 반복
   - 기대 결과 (요구사항) - 반복되면 주의 (기준 TBD-01)
   - 현재 결과 (고정 임계값 방식) - 1일 13:12 주의, 튐이 계속되는 동안 주의 유지 (AI도 같음, 2026-11-07)
   - 검증 목적 - 반복 이상 감지 (STK-11, SYS-07)

6.
   - 번호 - 6
   - 이름 (코드) - 지속적 급상승 (`sharp_rise`)
   - 무슨 일이 일어나나 - 시간당 +2mA 상승, 최대 +7mA에서 유지
   - 기대 결과 (요구사항) - 점검권고
   - 현재 결과 (고정 임계값 방식) - 1일 03:12 주의 → 1일 07:12 점검권고
   - 검증 목적 - 급한 이상 감지 (STK-01)

7.
   - 번호 - 7
   - 이름 (코드) - 데이터 끊김 (`data_loss`)
   - 무슨 일이 일어나나 - 3시간 동안 측정값 없음
   - 기대 결과 (요구사항) - 센서장애 → 복구 시 이전 상태
   - 현재 결과 (고정 임계값 방식) - 1일 00:48 센서장애 → 1일 03:12 정상
   - 검증 목적 - 고장과 이상 구분 (STK-06)

- 시각은 가상 시간이며 "N일 HH:MM"은 시작(0일 00:00)부터 경과 시간이다.
- 보안 시나리오(인증 없는 장치 접속, 다른 설비 토픽에 발행)는 데이터가 아니라 통신 시험이라 4단계에서 따로 다룬다 (SYS-13a~c).

### 7.3 검증 도구

- **정적분석**: 코드를 **실행하지 않고** 읽어서 문제를 찾는다.
- **동적분석(동적 테스트)**: 코드를 **실행해서** 결과를 확인한다.

1.
   - 도구 - ruff
   - 정적 / 동적 - 정적
   - 무엇을 찾나 - 코딩 규칙 위반, 버그가 생기기 쉬운 패턴, 보안 취약 패턴 (예: 문자열로 SQL 조립)
   - 자동차 업계 대응 도구 (참고) - Helix QAC, Polyspace Bug Finder (MISRA 규칙 검사)

2.
   - 도구 - mypy
   - 정적 / 동적 - 정적
   - 무엇을 찾나 - 타입 불일치 (예: None일 수 있는 값을 숫자처럼 사용)
   - 자동차 업계 대응 도구 (참고) - C/C++은 컴파일러·정적분석기가 담당

3.
   - 도구 - pytest
   - 정적 / 동적 - 동적 (블랙박스)
   - 무엇을 찾나 - 입력 → 기대 결과가 맞는지. 다르면 기능 결함
   - 자동차 업계 대응 도구 (참고) - VectorCAST, TESSY (단위 테스트)

4.
   - 도구 - pytest-cov
   - 정적 / 동적 - 동적 (화이트박스)
   - 무엇을 찾나 - 테스트가 한 번도 실행하지 않은 코드·분기. 테스트 누락을 찾는다
   - 자동차 업계 대응 도구 (참고) - VectorCAST, TESSY (커버리지, MC/DC)
